# Portal analytics and QA readiness

Updated: 2026-11-11

## What the game measures

| Surface | Data available | Limits |
| --- | --- | --- |
| Owned website | Consent-gated visits, shell/load funnel, menu actions, tutorial step start/complete/explicit exit, queue joins/cancellations/failures, match starts/ends/exits; match mode, win/loss, wait/duration bucket, fixed join-failure category; build, language, broad viewport class, and optional short `?ref=` tag. | Match dimensions are daily aggregates. Events carry a random session ID scoped to the current browser session; no account/player/match/lobby ID, name, password, IP field, map click, or free-text failure reason enters the event record. The request IP may appear in separate technical security logs. This collector does not measure cross-session retention or unique people. Closing a tab is not an observed match exit. |
| Poki | Official SDK `gameplayStart`, `gameplayStop`, loading signal, and `measure` funnel events. Match results map to `win` or `loss`; event measures are suppressed while an ad is active. | Use Poki's dashboard for its available player, playtime, retention, ad, and load metrics. The portal's data is separate from our website data; no player IDs are exported to our server. |
| CrazyGames | Official SDK gameplay and loading lifecycle, including start/stop around playable matches. | The current native bridge does not send arbitrary custom funnel events or fabricate whole-game completion percentages. The [official SDK guide](https://docs.crazygames.com/sdk/game/) says focus changes are handled by CrazyGames; call start/stop for game breaks, not blur. Use the CrazyGames dashboard for its supported aggregates; detailed tutorial or match drop-off is not available there through the native SDK. No third-party collector is bundled. |
| Jest | Official SDK custom events for curated funnel steps, `getEntrySource()` reduced to its source type, `markGameLoaded()`, and `markFirstMilestone()` when the first tutorial becomes playable or a match starts. Guest progress is stored under Jest's stable `playerId`; D1–D7 notifications are scheduled only for registered players. | Entry campaign names, IDs, UTMs, player IDs, and payload details are not attached to custom events. Jest owns its dashboard and retention reporting; these data are not copied to our analytics store. |

The shared client event contract accepts only enumerated values. The owned site's consent policy is `2026-11-10`; a previous choice is requested again before the expanded match categories can be sent. Event schema 3 rejects account/player identity fields at ingest. The first-party analytics endpoint retains event files and aggregates for 90 days. Historical account cohorts from schema 2 remain until deletion or expiry, and account deletion still scrubs their linked pseudonyms.

The owned-site browser sends only a temporary session ID after consent; it never reads or includes the game account ID. The endpoint does not receive player, match, lobby or IP fields in event payloads. Request IPs remain separate technical connection metadata and may appear in security logs. The schema 2 archive may still contain channel-scoped account pseudonyms until its 90-day expiry; verified account deletion removes those legacy memberships.

## Churn and conversion signals

- Tutorial start, individual step completion, and explicit early exit show where an engaged player stops. Closing a tab is not observable as an intentional churn event.
- Queue start, join, cancellation, wait bucket, and fixed failure category expose matchmaking friction without storing raw server errors.
- Match start, result, mode, and duration bucket distinguish conversion to play from completed play. `match_exit` counts only explicit menu exits before a result.
- Website reports include event counts and distinct sessions per UTC day. They do not calculate cross-session retention or unique people, and they do not reconstruct an individual journey. Historical schema 2 cohorts are labeled separately and expire after 90 days.
- Portal dashboards remain separate. We cannot claim cross-portal unique users, cross-device people, player demographics, or a single cross-platform retention rate.

The portal measures initial download through `Gameplay start`; its 50 MB initial cap (20 MB for mobile-home eligibility) cannot be confirmed by the local package validator. Verify that WOU work preserves CrazyGames' native social-login flow and identity, plus guest progress behavior. A previous code audit found guests without a CrazyGames identity fall back to a remote anonymous profile and the SDK account-link prompt has no caller, so guest progress linking is not implemented. The [official account requirements](https://docs.crazygames.com/requirements/account-integration/) recommend guests play without an in-game account unless it can be linked, and differ between Basic and Full implementations. The private QA tool must verify the selected launch tier, guest behavior, external API/multiplayer review, initial download, and SDK lifecycle.
- **Jest:** target Basic Launch only. The latest `./sow jest` fails its WOU-marker check, and the ZIP on disk is stale. After a valid package exists, the official checklist must verify mobile readiness, SDK health, `getPlayer()` or `getPlayerSigned()`, guest progress keyed by stable `playerId`, registration, the first playable milestone, and D1–D7 notifications for registered players. No external links or in-app advertising are intended. The Simulator still needs to verify automated checks; mobile review covers iOS Safari and Android Chrome, under-10-second time to interactive, and 10+ minutes of stability.
